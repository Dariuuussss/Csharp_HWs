# ДЗ 9.2 — Интерфейсы и инверсия зависимостей

## Часть 1

### Задача 1.1

**1. Интерфейс `IDamageable` позволяет работать с любыми объектами, которые могут получать урон. Благодаря этому метод `ProcessDamage` подходит и для игроков, и для ловушек, и для других классов с этим интерфейсом. Это называется полиморфизмом: разные объекты можно обрабатывать одинаково через общий интерфейс. Если появится новый класс с `IDamageable`, менять `GameSystem` не придётся.

**2. Формально `Trap` выполняет требования объявления интерфейса, потому что реализует все необходимые свойства и методы. Однако его поведение необычно: `TakeDamage` всегда возвращает `false`, а значение `HP` не изменяется. Это может запутать код, который ожидает уменьшения здоровья после получения урона. Если по договорённости `TakeDamage` должен уменьшать HP, такое поведение уже нарушает смысловой контракт и его стоит исправить или явно описать.

**3. `HealthPotion` реализует только `IHealable`, поэтому его нельзя передать в `ProcessDamage` как объект `IDamageable`. При попытке добавить зелье в `List<IDamageable>` компилятор выдаст ошибку несовместимости типов. Кроме того, метод `ProcessDamage` вызывает `TakeDamage`, а у зелья такого метода нет. Поэтому для лечения нужен отдельный метод `ProcessHeal`, работающий с `IHealable`.

**4. Потребуется изменить классы `Player` и `Trap`, потому что оба реализуют `IDamageable`. В каждом классе нужно будет добавить свойство `IsDead` с подходящей логикой. Если этого не сделать, возникнет ошибка компиляции: классы не выполняют все требования интерфейса. Это показывает, что изменение контракта интерфейса влияет на классы, которые его реализуют.

### Задача 1.2

| Утверждение                                                      | Abstract class | Interface |
| Может содержать поля с конкретными значениями                    | +              | −         |
| Может иметь полноценный конструктор                              | +              | −         |
| Один класс может наследовать/реализовывать несколько таких типов | −              | +         |
| Может содержать реализацию метода по умолчанию                   | +              | +         |
| Может объявлять свойства без реализации                          | +              | +         |
| Может быть использован как тип поля или переменной               | +              | +         |
| Может наследовать классы                                         | +              | −         |
| Может содержать приватные методы                                 | +              | +         |

**Комментарии к таблице**

1. **Поля** Абстрактный класс может хранить значения в полях. Интерфейс не может содержать обычные поля экземпляра.
2. **Конструктор** У абстрактного класса может быть конструктор для инициализации данных. У интерфейса нет конструктора экземпляра.
3. **Множественное наследование** Класс в C# может наследоваться только от одного класса, но реализовывать сразу несколько интерфейсов.
4. **Реализация методов** Абстрактный класс может содержать готовые методы.
5. **Свойства** И абстрактный класс, и интерфейс могут объявлять свойства без реализации. Конкретный класс должен реализовать необходимые члены.
6. **Тип переменной** Оба типа можно использовать при объявлении переменных и полей. Это позволяет работать с объектами через общий тип.
7. **Наследование классов** Абстрактный класс может наследоваться от другого класса. Интерфейс не наследует классы, но может наследовать другие интерфейсы.
8. **Приватные методы** Абстрактный класс может содержать приватные методы для внутренней логики.

**Дополнительный вопрос**

Я бы создала общий абстрактный класс `Character` и интерфейсы `IDamageable`, `IInteractable` и `IHealable`.

**Схема наследования**

```text
IDamageable
    | (реализует)
Character (абстрактный класс)
    - Player: IInteractable, IHealable
    - Enemy
    - NPC: IInteractable
```

Все три персонажа имеют общие характеристики, например имя и здоровье, поэтому удобно вынести их в абстрактный класс `Character`. Там же можно реализовать получение урона через `IDamageable`. Интерфейс `IInteractable` нужен для персонажей, с которыми можно взаимодействовать и открывать диалоги. Интерфейс `IHealable` нужен только игроку, поскольку по условию только он восстанавливает здоровье.

Абстрактный класс я выбрала для общей логики и данных персонажей, а интерфейсы — для отдельных возможностей. Такой подход помогает не дублировать код и добавлять новые классы персонажей без изменения существующей структуры.
